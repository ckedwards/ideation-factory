# Implementation plan

**Status:** plan. Where to start building the backend, and in what order. The design it builds is in `mvp/`: [overview](mvp/architecture.md), [backend](mvp/architecture-backend.md), [cli and skills](mvp/architecture-cli.md), [front end](mvp/architecture-frontend.md), and [scale concerns](mvp/scale-concerns.md).

## Where to start

**Start with the edit-command engine and comment anchoring, as pure TypeScript with no server.** Then wrap it in a thin vertical slice, so the whole agent loop works early.

- **It's the riskiest piece:** block IDs, the plain-text form comments are matched in, applying batches, conflicts, and re-anchoring uploads. If that's wrong, nothing else matters. If it's right, the rest is fairly standard web-app work.
- **It needs no platform.** It's pure functions, so it can be built test-first and is unaffected by the open questions in the [Rivet](mvp/spike-rivet.md) and [Better Auth](mvp/spike-better-auth.md) spikes.
- **Test data already exists:** the prototypes' offline-sync idea (versions, a moved section, outdated comments) and the `mvp/` docs themselves make good fixtures.
- **Auth is the obvious first step, but not the right one here.** It's commodity work, and the [Better Auth spike](mvp/spike-better-auth.md) hasn't decided it yet. Starting there would postpone learning on the parts that could sink the project.

Storybook runs on Node, so confirm it works with Bun workspaces first | Every piece of the UI can be seen and checked, in every theme, before a page uses it |
| **8. Web app** | Pages and routes on the API, with each page's own components beside it and the building blocks from `ui` (see [Components first](mvp/architecture-frontend.md#components-first)), in five parts: **1. built:** the app itself: Vite, TanStack Router and Query, the API moved under `/api` so pages can have paths like `/teams/mobile`, the built app served by the app nodes, signing in through the browser's session, and `web`'s own Storybook, its stories tested in a CI job of their own; **2. built:** the idea page: a file with its diagrams, comments level with their text, commenting, replying and resolving, live. Its comments live in [TanStack DB](https://tanstack.com/db): a collection fed by the idea's WebSocket (`/api/ideas/{idea}/live`, its events carrying the comment, not just its ID), each write showing at once and taken back if the server refuses it. Reviews and approvals (step 9) use it too; Query keeps everything fetched, like files, versions and lists; **3. built:** addresses and versions. Ideas are numbered in their team like pull requests (`/mobile/idea/9`, someone's own at `/@riley/idea/3`), with an overview of what happened to them, their files at `/files` (`?v=` for an older version, read only, with its comments where they were then) and the changes between versions at `/changes/1..3` as a redline; a versions panel picks both, and a new version arrives live (the latest view moves on to it, and says so). A moved idea keeps its old address. Comparing against `main` waits for the server to know an idea's branch; **4. built:** the lists. Home (your ideas, and what changed in others'), Ideas (everything you can see, newest change first, and search), Teams (`/teams`, and a team's page at `/mobile` with its ideas and members), a person's ideas at `/@riley`, and Groups (`/groups/security`). List rows carry each idea's address, its team and owner by name, its description and its open comments. Still to come: your teams in the nav and a Join button (the API doesn't yet say which teams you're in), and Open and Closed filters once ideas can close (step 9); **5. built:** settings: your teams in the nav and asking to join; a team's or a group's settings (members, roles, join requests, and a team's handle, name and rules for new ideas); an idea's sharing and the move wizard; and your own (name and handle, passkeys, where you're signed in, and the apps and tokens that act for you), with passkey sign-in on the sign-in page. A handle, a person's or a team's, can change, and the old one keeps leading to its owner (`/@old/idea/3`, `/oldteam/idea/9`) until someone else takes it: handle aliases, beside the idea aliases. A person's handle changes through Better Auth (its username plugin is immutable now), so its user and the directory's stay in step. Site admins can release a squatted handle, a person's or a team's, with an operator command beside `deactivate` in `admin.ts` (a site admin page comes later): its owner gets a generated handle, its aliases go, and links through it stop working, which is why it's an admin's decision | |
| **9. The rest** | What 1.0 still needs, in six parts, suggested edits first because remote editing is what sets the product apart: **1. built:** suggested edits. A suggestion is a comment on a selection with a replacement for its text, so it anchors, follows edits, takes replies and is attributed like any comment. Anyone who can comment can suggest; people with edit access accept or reject. Accepting applies a `replace` built from where the text is now, as a new version whose step addresses the suggestion; accepting several at once is one version with a step for each, and one whose text overlaps another's, or whose text has changed or gone, stays open and says why. Rejecting is immediate, one at a time. In the web app (Suggest an edit in the selection menu, the change shown in its card, Accept and Reject, accepting several), the cli (`ideaf comment suggest`, `accept`, `reject`) and the API. A section's suggestions (a rewritten body) come later; **2. built:** editing in the browser, through the idea's **draft**: one per idea, kept by the idea actor, shared by everyone with edit access and live for all of them, always on the latest version. Editing adds changes to it (a block's new source, new text, a deletion; a heading edits its title and deletes its section), and accepting a suggestion can add it to the draft instead of making a version. Every change is checked as it's added: an edit or deletion carries the block as it read (`was`), so one made against something that has changed since is refused as outdated, never merged by guessing. The draft is rebuilt on whatever the latest version is, so a version made elsewhere (an agent's batch, an upload) marks the changes it overtook as outdated, and committing waits until they're undone or redone; such a version needs confirming first (`draft_outdated`; `--outdate-draft` in the cli, a dialog in the web app). Committing makes one version, a step per command, accepting the suggestions in it; discarding asks first, as the draft is everyone's. A block's new source becomes the smallest `replace` (core's `blockEdit`), so comments on the words that didn't change stay exact. Built in core (`draft.ts`), so the server and a future full editor share it: the block editor is the first client of the draft, not its shape. In the API (`get_draft`, `change_draft`, `undo_draft_change`, `commit_draft`, `discard_draft`, `accept_suggestions` with `into: draft`) and the cli (`ideaf draft show | commit | discard`, `ideaf comment accept --draft`). Agents' batches and uploads still make versions directly. Still to come: moving a section by dragging it in the contents, and creating, renaming and deleting files; **3.** reviews and approvals (see [Reviews](architecture.md#reviews)), in three pieces: **a. built:** statuses, reviewers, verdicts and closing: open states set by people, verdicts on a version (Request changes and Reject standing until withdrawn or dismissed), closing as accepted or rejected and reopening, by anyone with edit access, with Open and Closed filters on the lists. The status and its history and the verdicts are in the idea actor (`list_reviews`, `set_status`, `close_idea`, `reopen_idea`, `review_idea`, `dismiss_review`, live as `status` and `review` events); reviewers are a flag on the directory's access grants (`set_reviewer`), so removing someone's access takes them off too. In the cli (`ideaf review …`, `status`, `close`, `reopen`) and on the idea's overview (its Review section); **b. built:** the team's approval requirements, worked out live and needed to close as accepted, and groups added as reviewers. They're on the team in the directory (`set_team_requirements`, maintainers and admins), which checks them against an idea's counting approvers and open threads (`list_reviews` shows the checks; `close_idea` refuses with blocked until they're met). A rule's groups are asked to review when an idea goes out of draft, is created out for review, or moves into the team while in review. In the cli (`ideaf team requirements`) and the web app (team settings, and the overview's Review section). Lists don't show requirements yet: that needs each idea's reviews in the index; **c. built:** pending reviews, kept by the idea actor and submitted at once with a verdict. A comment, suggestion or reply added with `pending` is stored like any other (it follows new versions) but only its author sees it, and it sends no live event; it can be changed or deleted until `review_idea` publishes all of them, with a verdict or on their own (`discard_review` throws them away). Others can't reply to, resolve or accept one, and it doesn't count as an open thread. In the cli (`--pending` on `ideaf comment add`, `suggest` and `reply`; `ideaf comment edit` and `delete`; `ideaf review submit` and `discard`) and the web app (Add to review in the selection menu and on replies, Pending on the cards, a banner on the files page, and submitting from the overview's Review section); **4.** the inbox and watch levels, in two pieces: **a. built:** the inbox for direct participants. An idea's actor sends each write's events (a version, a comment or suggestion, a reply, a verdict, a status, a suggestion decided) through the directory's queue; the directory writes them to the inboxes of its owner, people asked to review (every member of a group, as if asked by name), people who took part and subscribers, one row per idea (the latest event and how many are new), leaving out whoever did it (but not their bots, unless they turn that off). Review requests reach you even if you unsubscribed. Read, Done (until something new), Subscribe and Unsubscribe; access is checked when the inbox is read, so losing access hides an idea's rows. In the API (`list_notifications`, `count_unread_notifications`, `mark_notifications`, `get_subscription`, `set_subscription`, notification settings), the cli (`ideaf inbox show | read | done | back | settings`, `ideaf subscribe`, `unsubscribe`) and the web app (Notifications with its badge, opening an idea marks it read, Subscribe on the overview, the setting); **b. built:** team watch levels: participating (the default), active (every idea out of draft, up to and including its close) or all, set by anyone for any team (`get_team_watch`, `set_team_watch`; your teams carry theirs). Nothing is written per watcher: a watched team's events join the inbox when it's read, as "watching", for ideas you can see, from the last 30 days, leaving out your own events, ideas you're already involved in and ideas you unsubscribed from; your read and done marks on them are kept as marks. In the cli (`ideaf team watch`) and the web app (the team page's Notify me about, moved from `ui` to `web`, and All or Active beside the team in the nav); **c. built:** email notifications over the SMTP settings sign-in codes already use, from their own sender (`IDEAF_NOTIFY_FROM`), from the inbox's events (see [Emails](architecture.md#emails-and-messaging)). On by default for the ideas you're involved in; per person, `involved`, `review-requests` or `off`, bundled (an email per idea once it's been quiet for 5 minutes, at most 30 after its first update) or a daily digest, and the teams you watch emailing too (off by default). The directory queues a row per person per event for those who want it, and sends on an actor alarm, checking access, unsubscribing and settings as it sends; reading an idea first, or marking it read or done, drops what was waiting. Each email says why, threads per idea, has headers for mail rules (`X-Ideaf-Reason`, `X-Ideaf-Idea`, `X-Ideaf-Team`, `List-Id`) and a signed one-click unsubscribe (`List-Unsubscribe`, `/unsubscribe`). In the API (the notification settings), the cli (`ideaf inbox settings --email … --cadence … --email-watching`) and the web app (Settings, Notifications); **5. built:** the hosted MCP server at `/mcp`, from the same operation registry, with step 6's part 4. The operations marked `mcp` in their definitions are its tools, 25 of them, for what agents do: finding and reading ideas (`list_ideas`, `search_ideas`, `find_idea`, `get_idea`, `show_blocks`, `pull`, `create_idea`), editing with commands (`preview_edit`, `edit`), comments and suggestions, the draft, reviews (`list_reviews`, `review_idea`, `set_status`), the inbox and `whoami`; sharing, teams, tokens and settings stay with people. A tool call runs the API's own handler through the same checks (`runOperation`). It's stateless (streamable HTTP, a JSON answer per request). Sign-in is Better Auth's `mcp()` (the OAuth provider, with the MCP server as a second resource and its protected-resource document) and `cimd()`: a client identifies itself by its metadata document's URL, fetched over Better Auth's transport (public addresses only, pinned, no redirects, rate-limited and cached), and the consent page names it and where its document is, starting on a bot for you named after it. Its tokens are 15-minute JWTs for `/mcp`, checked by signature, and aren't taken by the API (nor the API's by it); personal tokens work at both. Any client may sign in unless `IDEAF_MCP_CLIENT_HOSTS` lists the hosts allowed. Still to do: sign in from each real client (Claude Code, Claude.ai, VS Code, ChatGPT, the MCP Inspector), as the spike planned; Claude Code's real document was fetched and accepted in development; **6.** deployment and the load test, in four pieces: **a. built:** files in an S3-compatible bucket (`S3FileStore`, on Bun's S3 client, when `IDEAF_S3_BUCKET` is set; SeaweedFS in CI), and the app on an engine of its own (`RIVET_ENDPOINT`, with its namespace and token passed to the app's actor client). Checked against the bundled 3.0 engine run on its own: sign-in and ideas work, and survive the engine restarting. A new engine waits about a minute before it admits its storage (`storage.balancing.destination_stability_ms`, which must exceed 35 s), and RivetKit exits the app before then, so the app runs under a supervisor that restarts it: checked, the second start serves; **b. built:** the one-VM Compose (`deploy/one-vm/`): Caddy for TLS (Let's Encrypt, an internal ACME server, your own certificate files such as an internal CA's, or Caddy's local CA to try it out; chosen over nginx and certbot, which left a renewed certificate unserved until a reload), the app (its image built with the web app, production dependencies only), the engine (the pinned binary, its bucket SeaweedFS's or your cloud's) and SeaweedFS, a setup step making the engine's node pool, and the app trusting an internal CA's certificates in `ca/` for its own connections. Checked from nothing: up in 83 s, sign-in, an idea's file in the bucket, and the idea after an engine restart and a full down and up; each TLS mode but public Let's Encrypt (the internal ACME server was Pebble); **c. built:** the three-VM Compose (`deploy/three-vms/`): `node.yaml` on each VM (the app and an engine advertising its private address; the engines cluster through the bucket), `lb.yaml` (Caddy round-robin with health checks, the same TLS modes) or a cloud load balancer, an external bucket, and `try-locally.yaml` for all of it on one Docker host. The Rivet spike's fail-over checks, run on it: no acknowledged write was lost in any test. An app's crash fails its actors over in seconds. A whole node's loss (its engine too): on Rivet 3.0.6 its actors moved in 100 to 130 s in each of 5 runs on a fresh cluster, but they sometimes stay stuck until the node returns. That's 2 of 3 runs on a cluster already through several kills, and 3.0.0 always. In those runs, storage the dead engine held stayed unavailable, and actors waited on stop commands to it. Rivet tracks it as rivet-dev/rivet#5957; rescheduling a stuck actor through the engine's API brings it back. A fix we tried (counting `endpoint_unresolved` as a lost peer) didn't help; **d.** the load test, with k6, and its results in scale concerns | Everything 1.0 promises, and that it holds up under load |

## Local development

Day-to-day work needs only Bun, plus Node for Vite and Storybook:

- **Actors:** in development RivetKit starts a local Rivet Engine itself: a binary that comes with the npm package, storing data on the file system. There's nothing to install or run separately, and no Docker. `bun run dev` and `bun run test` point it at `.data/` (through `RIVETKIT_STORAGE_PATH`, which must be set before Bun starts; setting it from code doesn't reach the native runtime). The engine keeps running after the app exits; `bun run engine:stop` stops it.
- **Files:** a local folder, behind the same files interface as S3 (Bun's built-in S3 client) in production. One set of contract tests runs against every implementation: store by hash, read back, a missing key, the same content stored twice.
- **The real engine and buckets are for the [Rivet spike](mvp/spike-rivet.md):** the 3.0 engine, SeaweedFS and RustFS, in Docker Compose under `experiments/spike-rivet/`. The local engine is 2.x; run the 3.0 engine in Docker now and then before relying on behavior that might differ: queue ordering under load, sleep and wake, live updates reconnecting.

## First milestone: a walking skeleton

The demo for the pitch, with no UI, no real auth and no directory yet, all on a laptop (RivetKit's local mode and a local folder for files) with a dev token:

1. `ideaf start`, then `ideaf sync` a folder of Markdown.
2. Add a comment on a section, through the API.
3. `ideaf edit` a batch that moves that section and rewords it. The comment follows.
4. `ideaf pull` the result into the repository.

## Decisions to make early

Each is hard to change once there's data. **All four are decided, in step 1:** see [core](mvp/core.md).

1. **Block IDs:** how they're assigned and kept across versions, and how files get IDs, so renames work.
2. **The source map:** the Markdown parser's positions (mdast) give the map from plain text back to source. Settle the library now, because the web app has to use the same one to place comments.
3. **What's stored where:** the idea actor's tables (versions, steps, comments, an anchor per version), and the version manifest format.
4. **The batch format,** as a JSON Schema, because the cli, MCP and the web app all produce it.

## Testing approach

- **Golden tests for `core`:** fixtures of "before" files, a batch or an upload, and the expected files, comment positions and states (exact, moved, changed, outdated).
- **Contract tests for the files interface:** the same tests for the local-folder, in-memory and S3 implementations; the S3 run is against SeaweedFS in the Rivet spike.
- **Shared fixtures:** the cli and the server use the same `core`, so content hashing and batch validation are tested once.
- **A large-idea fixture** (dozens of files, hundreds of comments), for scale concern 4.
- **Stories for `ui` and `web`:** axe accessibility checks on every story in CI, each package's in its own job.

## Follow-ups

Smaller pieces of work that came up along the way and aren't part of a step yet.

- **People's names in each idea, if the directory gets busy:** an idea page names its people with one batched `get_people` call. If the load test shows the directory hot, each idea can keep its people's names in its own SQLite, updated in the background when someone changes their name or handle (renames are rare, reads constant), so pages, comments and live events name people with no directory call.
- **App components out of `ui`,** as step 8 builds the pages that use them: components that decide something about the product move to `web`, beside their page, built from `ui`'s building blocks. `WatchSelect` (the watch levels, what each means, which to highlight) is the clearest; `StatusControl`, `IdeaState`, `ApprovalProgress`, `ViewInVersion` and the idea page's comment and heading components are likely too.
